## Thread/topic: tutorial-timing-and-welcome-screen

**Sections likely affected:** 3, 6, 9

**Customer-facing:**
The onboarding tutorial's guide box no longer flashes in the wrong spot before snapping into place above "Set Filters" -- it now only ever appears already correctly positioned. First-time users also now see a one-time welcome screen before Home: it introduces RiftAcademy, flags this as an alpha build, and previews the short Vendetta-focused tutorial that follows.

**Team-facing:**
Two items from this session, in `fix/tutorial-timing-and-welcome-screen` (branched off latest `integration`).

1. **Tutorial bubble no longer flashes at the wrong position before snapping.** Round 2 fixed the underlying race (the bubble's `measureInWindow` sometimes catching the target's pre-scroll position, re-measuring 400ms later) but that still left a visible flash-then-snap, since the bubble rendered the INSTANT a `targetRect` first arrived, correct or not. Per Ashwin's follow-up: `TutorialCallout` now holds the bubble hidden for `STEP_SETTLE_MS` (500ms) after every step change, not just the one known-racy step -- a fresh timer keyed on `currentStep.id`, reset on every transition. Since 500ms comfortably exceeds the existing 400ms post-scroll re-measure delay in `SettingsScreen.tsx` (unchanged from round 2), by the time the bubble is allowed to render, any in-flight re-measure has already landed, so it only ever appears already in the right place. Verified live: the `setFiltersCTA` step's bubble now renders directly above the button with no visible snap, confirmed via a screenshot taken immediately after the interaction that triggers the race.
2. **New one-time welcome/alpha screen before Home.** `WelcomeScreen.tsx`: RiftAcademy wordmark, an "ALPHA" pill badge, two lines of body copy (alpha-build framing + feedback-bubble pointer, then a preview of the upcoming Vendetta tutorial), and a single "Let's go" button. Gated by a new `hasSeenWelcome` flag (own key, in both `db.web.ts` and `db.native.ts`, deliberately separate from `hasSeenTutorial` -- two independent one-time gates that happen to run back to back, not one combined flag). `App.tsx`'s `AppShell` now does a one-time async check of that flag BEFORE the `Stack.Navigator` ever mounts (a navigator's `initialRouteName` can't be swapped after mount without an explicit reset) and picks `"Welcome"` or `"Home"` as the initial route accordingly; renders `null` for the brief window before that check resolves (in practice sub-frame, nothing visibly flashes). No changes to the tutorial's own logic were needed -- since `TutorialProvider`'s `hasSeenTutorial` check and the Welcome screen's `hasSeenWelcome` check are independent, and `TutorialCallout` only ever renders once its target's screen has actually mounted and registered a `targetRect`, the existing tutorial simply starts normally the moment Home mounts, whether that's immediately (returning user) or after a "Let's go" tap (first-time user) -- no special hand-off code between the two flows. Extracted `RiftWord` (the "Rift" + colored-suffix wordmark helper) out of `HomeScreen.tsx` into `src/components/RiftWord.tsx` since Welcome now needs the same treatment; `HomeScreen.tsx` updated to import it, behavior unchanged.

**New standing rule or convention worth capturing:**
None new -- the welcome/tutorial separate-flags pattern follows the same "don't let one seen-it-once gate reset another" convention already established for `hasSeenTutorial`/the batch-completion gate.

**Anything another thread working today should know before touching related code:**
`RiftWord` moved from a local function in `HomeScreen.tsx` to `src/components/RiftWord.tsx` -- import it from there, don't re-add a local copy in a new screen that needs the wordmark. `App.tsx`'s `AppShell` now renders `null` briefly on cold start while it resolves the initial route; if you add another gate that needs to run before the navigator mounts, extend that same check rather than adding a second independent async gate (which would race against this one and risk a route decided on stale state).
