## Thread/topic: normalized-rules-text

**Sections likely affected:** 6 (standing rules), 9 (log)

**Customer-facing:**
Nothing user-visible.

**Team-facing:**
Follow-up to `2026-08-07-drop-rules-pdfs-from-head.md`. Adds ligature-expanded copies of both rules files so ordinary ASCII search works: `core-rules-RUP4.normalized.txt` and `tournament-rules-RUP4.normalized.txt`, generated by `scripts/normalize_rules_text.py`, plus `docs/rules/ligature-words.md` listing every affected word.

The copies are a **search index, not a fork**. Line numbers are identical to the originals by construction — every substitution is within a line, and the generator asserts the line count is unchanged — so a hit at line 1932 of a normalized copy is the same rule at line 1932 of the original. The originals remain the citable source of truth. The generator refuses to run if NFKC would change any character beyond the three expected (`ﬁ`, `ﬂ`, `…`), so a future rules revision introducing a new compatibility character fails loudly rather than being silently rewritten.

Effect, measured on the Core Rules: `battlefield` 0 → 253 lines, `deflect` 0 → 14 (a Vendetta keyword), `first` 13 → 74.

**⭐ The finding that matters more than the fix: the corpus mixes both encodings.**

The ligature problem was described — by this thread, and in the handoff to RiftCore — as producing a **silent zero**. That is true for 62 of the 75 affected words. It is **not** true for the other 13, which appear *both* as a ligature and as plain ASCII. For those, an ASCII search returned *some* of the matching rules and silently dropped the rest.

**This is materially worse than a zero result, and it changes the exposure question RiftCore is currently working.** A search returning nothing invites suspicion and a second method. A search for `finalized` returning 20 hits looks like a complete answer while omitting 24 — there is no signal to investigate. `finalize`/`finalization`/`finalized`/`finalizing` is precisely the vocabulary RiftCore identified as "the FEPR core," and `flow` is a Vendetta keyword mechanic.

RiftCore's assessment (`RiftCore_Ligature_Exposure_Assessment_2026-08-07.md`) reasons that the v2 rebuild was structurally resistant because it read positionally by rule number rather than by term search, and that argument is unaffected — numeric anchors remain ligature-immune. What changes is the residual risk from the term searches that *were* run: the assessment assumed those failed visibly, and for these 13 words they failed invisibly instead.

**New standing rule or convention worth capturing:**
Extending the method note already recorded in the previous fragment:

> A text corpus derived from PDF extraction must be verified for searchability, not only for content fidelity.

Add: **check whether the corpus is internally consistent in its encoding, not merely whether it is normalizable.** A uniformly broken corpus fails safely — every search returns zero and the problem announces itself. A corpus that is broken in some places and correct in others returns plausible partial results, and nothing downstream can tell a partial answer from a complete one. Uniformity of a defect is a safety property; mixed encoding is the harmful case, and it is the one that looks healthier on inspection.

**Anything another thread working today should know before touching related code:**
- **If you searched these rules files by term at any point, and the term is in `docs/rules/ligature-words.md`, re-run it against the `.normalized.txt` copy.** Especially if you got a non-zero result and concluded you were done.
- Don't hand-edit the `.normalized.txt` files or `ligature-words.md`; regenerate with `python3 scripts/normalize_rules_text.py`.
- The count correction from the previous fragment stands: **778** ligatures in the Core Rules, not 526. 526 is the line count.
- Per RiftCore's assessment, `cards.json` and Core's own v2 documents are ligature-free (0 in each), so this is bounded to the rules files. RiftCore's recommended pre-flight check on Supabase `cards.rules_text`, which came from a different corpus (the Master Card Inventory CSV, migration 008), is still outstanding and is not addressed here.
